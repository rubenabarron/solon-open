# Build log 0003: the pilot intake form ships

Date: 2026-10-01 | Status: published

## What shipped

A visitor can now request a pilot from solonai.org without leaving the browser. The
"Start a pilot" calls to action point to an in-page form that verifies a Cloudflare
Turnstile challenge, stores the submission in D1, and emails a notification. The form
replaces the mailto links; the footer email stays as a fallback. A short privacy note
documents what is collected and why.

Two engineering notes are worth publishing:

- Pages Functions cannot hold a send email binding. The supported bindings subset does
  not include email, so the notification goes through a small internal relay Worker that
  owns the email binding and has no public URL; the Pages Function reaches it only
  through a service binding. The Worker fixes both the sender and the recipient, so the
  public endpoint can never address anyone else.
- The verification script had to move behind hydration. A script tag in the static HTML
  could execute before the page's own JavaScript was ready; when it mutated the widget
  container first, React hydration regenerated the tree and destroyed the widget, and the
  form could never obtain a token. The script now loads from the client component after
  hydration. The race was reproduced and the fix verified with a headless browser check.

## How it was verified

- 33 automated tests pass, including nine for the relay Worker and one that pins the
  non-POST route behavior. Type checks and the static build are clean.
- The site check suite reports 94 checks on the public site, including the new privacy
  URL in the sitemap and the canonical and redirect checks.
- Preview and production each served a real submission end to end: the row appeared in
  D1, the notification email arrived, and the test row was deleted afterward.
- The production race fix was verified with a browser assertion: no page errors, the
  token field present, and the verification script absent from the served HTML.

## What we learned

- Check the platform's actual binding support before designing around it. The email path
  had been designed as a direct binding; the platform supports only a subset on its
  static-site functions. A short documentation check moved one component of the design
  before anything shipped broken.
- Timing bugs hide behind "works on my machine". The form worked on the preview domain
  and failed intermittently on the custom domain, purely on script timing. A
  deterministic assertion (what must be true of the served HTML) turned a flaky symptom
  into a fixable condition.
- Keep the notification inside the trusted boundary. The relay Worker hard-codes the
  sender and the recipient and has no public address, so the browser-facing endpoint can
  only ever trigger one kind of email.
